Microsoft Graph v4 — Genuine Spec Bugs

45 tables where the Coral OpenAPI-to-DSL parsing produces wrong endpoints, queries, or audience targeting. These are NOT auth/license/tenant issues. Updated 2026-08-01: root causes re-verified against the live Graph v1.0 OpenAPI spec — the 45 failures are Graph-service realities the metadata does not encode, so fixes require curated per-operation overrides or a trimmed document, not a parser change alone.

Test Methodology

Each table was queried via Coral SQL using the following command pattern. Tables that returned a valid row (any data) passed; tables that returned an error were classified by error type.

SELECT 1 AS ok FROM microsoft_graph_v4.<table_name> LIMIT 1

Example raw Coral SQL query for a specific table:

coral sql \
  --task-id "<task_id>" \
  --intent "test if this table is functional" \
  --query "SELECT 1 AS ok FROM microsoft_graph_v4.agreementacceptances_agreementacceptance_agreementacceptances_agreementacceptance_listagreementacceptance LIMIT 1"

Total tables tested: 733 | Passed: 112 | Spec bugs identified: 45 | Auth/config failures: 576

Verified Update — 2026-08-01

The live Graph v1.0 openapi.yaml (36 MB, fetched 2026-08-01) was inspected to verify the root causes claimed in the original report:

  • The spec has one top-level server (https://graph.microsoft.com/v1.0) and no per-operation servers overrides — the "Wrong URL" parser fix is not implementable as written.
  • The spec has no x-ms-audience fields — the "Wrong Audience" fix cannot be derived from the document.
  • The "deprecated" operations (e.g. appCatalogs.appCatalogs.GetAppCatalogs) are still present and not flagged deprecated: true (only 79 ops in the whole spec carry the flag). The metadata is stale relative to the live service.
  • Coral 0.8.1 imported the document faithfully; these failures are host routing, retired endpoints, tenant-type limits, entity-scoped resources, and query restrictions that the OpenAPI metadata does not encode.

Conclusion: none of the 45 are fixable by editing microsoft_graph_v4/manifest.yaml (DSL v4 exposes a single base_url per surface, surface-wide headers, and no operation filtering). See the Solution section below.

Solution (2026-08-01)

▼

The 45 tables cannot be fixed by editing microsoft_graph_v4/manifest.yaml (DSL v4 exposes a single base_url per surface, surface-wide headers, and no operation filtering), and the OpenAPI spec provides no per-operation metadata to fix them automatically. Two workable options:

  1. Trim the document (no Rust, fastest). Vendor a corrected copy of the Graph v1.0 openapi.yaml into the source as file: with the 45 buggy operations deleted. The remaining ~700 tables all become genuine. Cost: the source diverges from upstream Graph metadata until coral supports filtering.
  2. Per-operation override feature (Rust in coral-spec/coral-engine). Add an optional per-operation map to the DSL v4 openapi surface, e.g. operations: <id>: { base_url, headers, enabled, required_inputs }, seeded with curated data for these 45 (hosts from Microsoft docs, retired ops disabled, audience-specific ops tagged). Requires a coral CLI release to take effect in this test environment.

Recommended: keep the P0–P3 priority, but reframe from "parser must respect servers/x-ms-audience" (not implementable as written) to "coral needs a curated per-operation override capability".
