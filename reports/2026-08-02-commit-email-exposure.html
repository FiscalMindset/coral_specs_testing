Exposed via commit metadata
Bottom line: the maintainers' real email addresses are publicly exposed in the git commit metadata of both withcoral/coral (origin) and FiscalMindset/coral (fork). This is not a file leak and not a breach — it is standard git/GitHub behavior, because every commit object permanently stores the author's git config user.email. Anyone can retrieve them without authentication via the GitHub API or git log on a clone.
What is NOT exposed in files: a full search of the working tree found zero personal addresses in any source, docs, config, or manifest. The only emails present in files are the deliberate public aliases security@withcoral.com and legal@withcoral.com.
Why it's easy to miss: GitHub's web UI hides the author email. The raw commit object served by the public API (GET /repos/{owner}/{repo}/git/commits/{sha}) and by git log --format='%ae' contains it in plain text.
Executive summary▶

While investigating the Coral repository, I found the personal email addresses of the main contributors are publicly exposed through the git commit author field. This affects both the origin repo and the fork, because forks copy the complete git history unchanged — the commit objects (and their SHAs) are byte-for-byte identical. The exposure is real, trivially retrievable by anyone, and currently present on 455 commits in the origin's main branch. Future exposure can be stopped in minutes with a GitHub setting; removing the historical exposure would require a destructive history rewrite.

The local clone used for this investigation is a copy of the fork (git remote -v → origin https://github.com/FiscalMindset/coral.git). Because a fork shares the full history, commit objects — and therefore author emails — are identical across origin, fork, and clone.
Key concept: a fork is not a new history — it is the same commit graph pointing at the same objects. Any email baked into a commit on the origin is automatically present on every fork and every clone, forever (unless rewritten).

Assessment — leaked or not?
Yes — the emails are publicly exposed via git commit metadata, on both origin and fork. But this is not a file leak and not a breach: it is standard git/GitHub behavior caused by committing with real email addresses instead of GitHub's noreply aliases.

Solution suggestions
  1. Enable "Keep my email addresses private" on GitHub (Recommended — stops future exposure)
    GitHub → Settings → Emails → check Keep my email addresses private. GitHub then rewrites the author identity of all future pushes to <id>+<username>@users.noreply.github.com.
  2. Update local git config on every contributing machine
    $ git config --global user.name  "Your Name"
$ git config --global user.email "<id>+<username>@users.noreply.github.com"
  3. Set the email per-repo (so forks/clones don't reintroduce the real address)
    $ git config user.email "<id>+<username>@users.noreply.github.com"
  4. Verify after pushing
    $ git log -1 --format='%ae'
  5. Rewrite history with git filter-repo (Optional / advanced — removes past exposure)
    $ git filter-repo --email-callback 'return b"<id>+<username>@users.noreply.github.com"'
$ git push --force --all
    ⚠ Warning: this changes every commit SHA, invalidates PR references, and requires everyone with a clone (including all forks) to re-clone or rebase. For a public repo with many forks this is usually not worth it — low payoff, high coordination cost.
  6. Not recommended
    Asking GitHub Support to redact emails — not available for standard accounts on public repos. git filter-branch — slow and error-prone; prefer git filter-repo.
