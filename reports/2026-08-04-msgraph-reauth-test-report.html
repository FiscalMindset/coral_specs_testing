Three compounding failures caused 30 PASS instead of expected ~120

1. Token expiry (the killer)▶

The battery run started at 00:13 UTC using the 12-scope az CLI admin token. The az token expires every 1 hour. After ~80 minutes (at 01:30 UTC), the token died, causing 481 expired_token failures on the retry.

The OAuth device code flow gives a 1-hour access token with NO automatic refresh. The keychain OAuth flow (used in v1 on Jul 31) auto-refreshes — that's why v1 worked.

Technical details: Why tokens expire▶

Microsoft's OAuth2 access tokens have a configurable lifetime. For interactive flows:

  • Default access token lifetime: 1 hour (3600s)
  • Default refresh token lifetime: 90 days (rolling for active use)
  • Keychain OAuth flow (interactive): Stores BOTH tokens, auto-refreshes
  • Device code flow: Can include offline_access scope for refresh tokens, but Coral's keychain isn't updated without interactive flow
  • az CLI token: 1 hour access, no refresh, manual re-login required

To extend token lifetime in Entra:

  1. Go to Entra admin portal → Applications → App registrations → Coral
  2. Manifest → set "accessTokenAcceptedVersion": 2 and configure token lifetime policies
  3. Alternatively use Conditional Access with "Sign-in frequency" set to 30 days

Why the keychain approach is best▶

The keychain OAuth flow (Strategy 1) works because:

  1. Interactive browser flow stores BOTH access token AND refresh token in macOS keychain
  2. Access token has 1h lifetime, but coral CLI auto-refreshes it using the refresh token
  3. Refresh token has 90-day lifetime (with rolling renewal for active use)
  4. So the battery can run for hours without token expiry issues

This is what v1 (Jul 31) used and got 127-129 PASSes.
