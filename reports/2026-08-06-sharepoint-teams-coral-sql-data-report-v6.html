Bottom line

The SharePoint surface of the microsoft_graph_v4 connector works end-to-end from zero. With only two seeded IDs (the site triple + the Code Snippets list id) we successfully walked the entire hierarchy: site listdrives → site columns 367 / content types 64 / permissions 0 → listlists 27 → Code Snippets list columns 31 / content types 2 / permissions 4 / items → item getfields + item permissions. The Document Library drive surface also works: drive metadata, root, recent, search, drive-item permissions — and the same drive ID doubles as an unbacked list, where columns/content-types/getlist all succeed.

The Teams surface is unexecutable from zero — and this is a spec gap, not a token gap. No Teams/Groups/Chats listing function exists anywhere in the catalog (1,428 Teams-ish functions, all require a team_id/group_id/user_id/chat_id). The site GUID is not a team or a group; user lookup returns no id column; the three …getcreatedbyuser roots return upstream 500s. There is no path to a first Teams ID.

Recommendations for Coral maintainers

  • Add a root Teams enumeration surface — GET /me/joinedTeams (list, no args) and/or GET /groups?$filter=resourceProvisioningOptions/Any(x:x eq 'Team') — otherwise Teams can never be reached from zero (F2).
  • Add an id column to getuserbyuserprincipalname and to the …getcreatedbyuser rows so users can be chained into user-scoped routes (F4).
  • Expose the filter optional on drives_driveitem_drives_listitems (F7) and drop sites_baseitem_sites_listitems (F8).
  • Remove or document the three 500-ing …getcreatedbyuser/…getlastmodifiedbyuser site/drive routes (F5).
  • Document the getbypath path argument format; current '/' and 'sites:/' values both 400.
